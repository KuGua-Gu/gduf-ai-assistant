## 第 1 页 · 小票是怎么变成一笔账的

**标题**：从一张小票到一笔账：OCR 链路的四个关卡

**页面要点**

1. 上传：`POST /api/ocr/upload`（multipart）→ 校验类型/文件头/大小 → 返回 `image_id`
2. 识别：`OcrService.recognize(image_id)` → 视觉模型只输出 JSON → `OcrResult`
3. 成卡：字段齐全生成确认卡片（`source="ocr"`）；缺字段先追问，不猜
4. 入账：用户确认后才写库（`/api/chat/confirm`）

**示意图（可直接画）**

```text
前端 ──上传──▶ /api/ocr/upload ──▶ data/uploads/<uuid>.png
                                        │ image_id
前端 ──/api/chat(image_id)──▶ Orchestrator ──▶ OcrService ──▶ 视觉模型
                                        │                        │
                                        ▼                        ▼
                                  TransactionDraft  ◀── OcrResult{amount, merchant, occurred_at, confidence}
                                        │
                                        ▼
                              确认卡片 ──用户确认──▶ 入账
```

**口播（60 秒）**

> 小票链路的难点不在“调一个模型”，而在把不确定的识别结果变成可控的数据。我们设了四个关卡：上传时校验类型和大小；识别时要求模型只输出固定 JSON；结果先变成草稿而不是直接入账；最后必须用户确认。任何一关失败都只会退回澄清或提示，不会污染账单。

## 第 2 页 · 怎么防止模型“编数字”

**标题**：三道防线：约束输出、校验字段、失败可见

| 防线 | 做法 | 效果 |
| --- | --- | --- |
| 输出约束 | system prompt 只允许 `{amount, merchant, occurred_at, confidence}`，禁止解释与代码块 | 减少自由发挥 |
| 解析校验 | 兼容 ```json 代码块 / 前后解释文字 → `json.loads` → Pydantic `OcrResult` | 脏输出不会进业务 |
| 重试与降级 | 解析失败重试 1 次（追加“只输出 JSON”）；仍失败抛 `OcrError` | 用户看到可读提示，不 500 |
| 低置信度 | `confidence < 0.8` 标记 `low_confidence`，并进入 `needs_review` | 前端提示“建议核对” |
| 无 Key 兜底 | 未配置 `VISION_API_KEY` 时退回桩实现 | 评审无 Key 也能跑通链路 |

**口播（60 秒）**

> 我们不迷信模型输出。第一，限制它只能输出固定字段；第二，解析时做结构校验，脏了重试一次；第三，置信度低于 0.8 就标记待核对；第四，模型不可用时给出可读提示并允许手动输入。所以即使模型出错，账单数据也不会被写脏——这是我认为比“识别率”更重要的工程底线。

## 第 3 页 · 效果、取舍与局限

**标题**：实测结果与边界

**评测**（配置 Key 后运行 `python scripts/eval_ocr.py`，把数字填进来）

| 指标 | 结果 |
| --- | --- |
| 样本 | 10 张合成小票（两种版式、±1.5° 倾斜） |
| 金额准确率 | 待填 |
| 商户准确率 | 待填 |
| 日期准确率 | 待填 |
| 三项全对 | 待填 |

**取舍**

- 用视觉大模型而不是模板 OCR：小票版式杂，视觉模型鲁棒性更好、开发更快；
- 用 OpenAI 兼容协议：可切换智谱 / 通义，不绑定一家；
- 不做本地 PaddleOCR 兜底（时间原因），但保留了 `OcrService` 协议，后续可插拔；
- 图片只保存在 `data/uploads/`，不入 Git；接口限制 10MB，避免大文件拖垮服务。

**口播（40 秒）**

> 评测口径是金额误差不超过 0.01 元、商户名允许包含、日期完全相等。我们没有追求 100%，因为合成小票和真实拍照仍有差距；我们更在意“错了能不能被发现、能不能纠正”。局限也写进了 README：没配 Key 时是桩数据，本地 OCR 兜底还没做。

## 现场演示脚本（1 分钟）

准备：服务已启动（`uvicorn app.main:app --port 8000`），`.env` 配好视觉 Key，浏览器打开 `/docs`。

| 步骤 | 操作 | 预期结果 | 讲解点 |
| --- | --- | --- | --- |
| 1 | `/api/ocr/upload` 上传 `receipt-01.png` | 返回 `image_id` | 上传校验 |
| 2 | `/api/chat` 带 `image_id` | 生成确认卡片，金额/商户来自图片 | 真识别 |
| 3 | 点确认 | `created=1`，账单列表出现 | 确认后才入账 |
| 4 | 上传一张**风景照**（非小票） | 返回可读提示或空字段转追问 | 失败不崩 |
| 5 | 上传一张**模糊小票** | `confidence` 低 → 提示核对 | 低置信度可见 |

> 备用：如果现场网络不通，把 `.env` 的 `VISION_API_KEY` 注释掉重启，链路仍可演示（走桩），口播说明“当前为离线兜底模式”。

## 预期提问与回答

| 问题 | 回答 |
| --- | --- |
| 识别准确率多少？ | 合成 10 张上是 X/10；真实小票会低一些，主要错在金额字体小和日期格式。 |
| 为什么不直接让模型回答“花了多少”？ | 模型会编数字；我们的数字只来自数据库和小票字段，查账也走 SQL。 |
| 模型返回的不是 JSON 怎么办？ | 提取 `{...}` / 代码块，失败重试一次，再失败转可读提示。 |
| 为什么不用 PaddleOCR？ | 时间不够，且小票版式杂；保留了 `OcrService` 协议，随时可替换。 |
| 没配 Key 的评审怎么跑？ | 自动退回桩实现，链路完整；README 已写明能力边界。 |
| 上传的图片会不会泄露？ | 只存本地 `data/uploads/`，不入 Git；演示用合成小票，不用真实票据。 |
